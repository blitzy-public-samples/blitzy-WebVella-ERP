# Critical Decision Review: PcGrid Bulk Archive and Bulk Delete

The WebVella ERP team added bulk archive and bulk delete to the PcGrid list view. The feature lets a user select several records on the rendered page and act on the whole selection in one request, with a reversible Archive and a permanent Delete. The document below records the five highest-risk decisions behind that feature, ordered from highest risk to lowest. Each entry states the decision, the rationale, the risk level, and the reviewer persona who should sign off. Three concerns drove the ordering: irreversible data loss, authorization, and the assumptions that resolved gaps the prompt left open.

The application code diff covers six files. The four PcGrid component files are `WebVella.Erp.Web/Components/PcGrid/PcGrid.cs`, `WebVella.Erp.Web/Components/PcGrid/Display.cshtml`, `WebVella.Erp.Web/Components/PcGrid/service.js`, and `WebVella.Erp.Web/Components/PcGrid/Options.cshtml`. The controller `WebVella.Erp.Web/Controllers/WebApiController.cs` gains the two bulk actions, and the new `WebVella.Erp.Web/Models/BulkRecordActionModel.cs` carries the request and per-record result models. The `Display.cshtml` view now renders the per-row selection checkboxes, the contextual toolbar, and the inline script, and `Options.cshtml` now exposes the admin configuration fields. Every new option defaults to off, so grids that do not opt in render as they do today.

## Decision 1: Permanent bulk delete removes records with no recovery path

- **Decision:** Bulk delete calls `RecordManager.DeleteRecord` once per selected record (`WebVella.Erp/Api/RecordManager.cs:1627`), which permanently removes each record. The feature builds no trash bin and no restore path. The new `BulkDeleteRecords` action (`WebVella.Erp.Web/Controllers/WebApiController.cs:1892`) mirrors the single-record delete transaction template (`WebVella.Erp.Web/Controllers/WebApiController.cs:1408-1438`). The `Display.cshtml` inline script guards the action with a count-aware native `confirm()` dialog that runs before the request fires, with wording such as "Permanently delete N record(s)? The records cannot be recovered."
- **Rationale:** The prompt asks for a true delete alongside a reversible archive, so the delete stays permanent at the data layer. The confirmation follows the repository destructive-action convention that pairs a native `confirm()` with a jQuery ajax call (`WebVella.Erp.Web/TagHelpers/WvFieldUserFileMultiple/form.js:19-45`). The repository ships toastr for transient notifications through the WebVella tag-helper chrome but provides no styled confirmation modal, so the count-aware wording carries the permanence signal that a modal would otherwise supply, and the script falls back to a native `alert()` when toastr is absent.
- **Risk level:** Critical. A wrong click destroys data for every selected record at once, and no undo exists.
- **Reviewer persona:** Data-integrity or security reviewer.

## Decision 2: Cross-origin requests cannot trigger the destructive bulk endpoints

- **Decision:** Both bulk actions call `IsBulkRequestOriginTrusted()` (`WebVella.Erp.Web/Controllers/WebApiController.cs:1646`) as the first step and return 403 through `BulkForbidden()` (`WebVella.Erp.Web/Controllers/WebApiController.cs:1668`) when the `Origin` or `Referer` host does not match the request host, or when the request carries neither header. The endpoints accept only an `application/json` body bound through `[FromBody]`.
- **Rationale:** The API authenticates with a cookie and applies no antiforgery token, which matches the single-record delete and update actions. A same-host `Origin` and `Referer` check, paired with the JSON-only contract, stops a cross-site page from driving a destructive bulk request with the signed-in user's cookie. The grid's own same-origin ajax passes the check without change, so the guard adds no friction to normal use.
- **Risk level:** High. Without the check, a malicious page could submit a bulk delete on behalf of an authenticated user.
- **Reviewer persona:** Security reviewer.

## Decision 3: Authorization runs per record and adds a field-level archive check

- **Decision:** The bulk path constructs the default `RecordManager`, which keeps `ignoreSecurity` false and `executeHooks` true (`WebVella.Erp/Api/RecordManager.cs:40`). `DeleteRecord` checks `EntityPermission.Delete` for each record (`WebVella.Erp/Api/RecordManager.cs:1647`), and `UpdateRecord` checks `EntityPermission.Update` for each record (`WebVella.Erp/Api/RecordManager.cs:984`). `BulkArchiveRecords` adds a field-level guard: when the `is_archived` field turns on `EnableSecurity`, `CurrentUserCanUpdateSecuredField()` (`WebVella.Erp.Web/Controllers/WebApiController.cs:1686`) confirms the user holds a role in the field's `CanUpdate` list, and the action returns 403 otherwise. An administrator and the system user bypass the field check, which matches the field-security convention the repository already uses.
- **Rationale:** Routing every record through the same data-layer calls that the single-record actions use means the bulk operations inherit the entity-level permission checks and lifecycle hooks. The entity-level `UpdateRecord` check alone does not cover a secured field, so the archive path adds the field-level check to stop a user from flipping `is_archived` on an entity whose field restricts update. A per-record check, rather than one check for the whole batch, stops a user from acting on any record they lack rights to, even when other records in the selection are allowed. The code never passes `ignoreSecurity: true`.
- **Risk level:** High. A weaker model would let a bulk request escalate beyond a user's single-record rights.
- **Reviewer persona:** Security reviewer.

## Decision 4: Live client logic lives in the Display view, not service.js

- **Decision:** The design places all live selection, confirmation, ajax, and refresh logic in an inline `<script>` block inside `WebVella.Erp.Web/Components/PcGrid/Display.cshtml`. The component `service.js` gains only Page Builder wiring for the new admin toggles.
- **Rationale:** A component `service.js` reaches the browser only through the Page Builder editor, served at `/api/v3.0/pc/{name}/resource/service.js` (`WebVella.Erp.Web/Services/PageComponentLibraryService.cs:52`), so runtime page logic cannot live there. The repository already runs live Display-mode behavior from an inline script inside the Display view, as `PcApplications` and `PcJavaScriptBlock` do (`WebVella.Erp.Web/Components/PcJavaScriptBlock/Display.cshtml:9-11`). The script wraps its body in an IIFE, keys its root container by the component node id (`pcgrid-bulk-root-{id}`), and selects the row checkboxes by that same key through a `data-grid-key` attribute, so several PcGrids on one page never collide.
- **Risk level:** Medium. A wrong placement would ship code that never runs on live pages and would break the feature silently.
- **Reviewer persona:** Frontend or architecture reviewer.

## Decision 5: Best-effort partial failure, the is_archived allowlist, and the admin entity name (ambiguities resolved)

- **Decision:** The server processes every selected record inside its own `DbContext` transaction, commits the records that succeed, rolls back only the records that fail, continues past a failure, and returns a per-record result list. Each result is a `BulkRecordActionResultItem` that reports the record id, a success flag, a stable result code, and a user-safe message, wrapped in the existing `ResponseModel` envelope. `BuildBulkResponse()` (`WebVella.Erp.Web/Controllers/WebApiController.cs:1807`) sets the status from the outcome: 200 when every record succeeds, 207 when some succeed and some fail, and 422 when none succeed. `TryNormalizeBulkRequest()` (`WebVella.Erp.Web/Controllers/WebApiController.cs:1845`) caps a request at `BulkActionMaxRecords`, which is 1000 (`WebVella.Erp.Web/Controllers/WebApiController.cs:1633`). Bulk archive writes only `is_archived` through `UpdateRecord` (`WebVella.Erp/Api/RecordManager.cs:952`), locks the write to the `BulkArchiveAllowedFields` allowlist (`WebVella.Erp.Web/Controllers/WebApiController.cs:1638`), rejects any other caller-supplied field name, and confirms from entity metadata that the field exists as a checkbox before it processes the batch. PcGrid supplies the target entity name from an administrator-configured `entity_name` option (`WebVella.Erp.Web/Components/PcGrid/PcGrid.cs:118`), because neither `EntityRecord` nor `EntityRecordList` carries one (`WebVella.Erp/Api/Models/EntityRecordList.cs:6-9`), and computes archive availability from the same metadata so Archive stays hidden unless `is_archived` exists as a checkbox on the entity (`WebVella.Erp.Web/Components/PcGrid/PcGrid.cs:597-640`).
- **Rationale:** A single record's failure must not abort the batch, so per-record isolation lets the good records proceed while the server reports which records failed. The single-record actions already wrap each operation in a `DbContext` transaction with commit and rollback and log errors through `LogService` (`WebVella.Erp.Web/Controllers/WebApiController.cs:1538-1585`), so the bulk loop applies that same wrapper once per record. The `is_archived` flag already serves as a soft-delete convention elsewhere in the repository, where a job archives records by setting `is_archived` to true (`jira-stories/STORY-006-notification-escalation-jobs.md`), so Archive reuses the field rather than defining new schema. The allowlist stops a caller from steering the write to any other boolean field, and the up-front metadata check stops a silent no-op when the field is missing or holds the wrong type, because `UpdateRecord` skips unknown fields without error. An administrator-configured entity name removes the guesswork, because the rendered records expose no entity name on their own.
- **Risk level:** Medium. Archive reverses easily and per-record isolation contains any single failure, but a blank or wrong entity name would target the wrong entity, so the availability gate, the request-size cap, and the per-record permission checks all still apply.
- **Reviewer persona:** Backend or reliability reviewer.

## Explicit callouts

- **Irreversible operation:** Decision 1 covers the permanent bulk delete. A per-record permission check and a per-record transaction guard the backend action, and a count-aware, permanence-explicit `confirm()` dialog in the Display script guards the action on the client.
- **Authorization decisions:** Decision 3 covers the per-record `EntityPermission.Delete` and `EntityPermission.Update` checks that run through the default `RecordManager`, plus the field-level check that guards a secured `is_archived` field. Decision 2 covers the cross-origin rejection that blocks a destructive request from an untrusted page.
- **Ambiguity-resolving assumptions:** Decision 5 resolves the missing entity name with an administrator-configured `entity_name` option, and treats `is_archived` as a pre-existing field with no schema or migration, locked to an allowlist and gated by an entity-metadata availability check. Decision 4 resolves the client-script placement question by following the repository's inline Display-mode convention.
