Executive Summary

The problem

One record at a time

Today the grid handles a single record per action, so managing a long list means repeating the same click many times.

Slow for large lists

Teams that clean up or triage records lose time to repetitive single-record work.

Accidental loss

A permanent delete with no guard rail puts users one wrong click away from losing data.

The feature answers all three problems while keeping the existing single-record flow untouched.

Context

What shipped

Multi-record selection

Per-row checkboxes and a select-all control add selection to the records on the current page.

Contextual toolbar

A toolbar appears once a user selects at least one record, and shows the live count next to the two actions.

Reversible Archive

Archive flips a boolean flag and reverses easily, so a lighter confirmation fits the action.

Permanent Delete

Delete removes records for good, so a count-aware confirmation names the permanence before the call.

Architecture

Server design

  • Two POST actions attach to the existing WebApiController and reuse its RecordManager field. A preflight step validates and de-duplicates the ids.
  • Each unique record runs in its own DbContext transaction. Delete calls RecordManager.DeleteRecord; archive sets is_archived to true and calls RecordManager.UpdateRecord.
// excerpt: WebApiController.BulkDeleteRecords
foreach (var id in recordIds)   // validated + de-duplicated by TryNormalizeBulkRequest
{
    using (var connection = DbContext.Current.CreateConnection())
    {
        bool transactionStarted = false;
        try
        {
            connection.BeginTransaction();
            transactionStarted = true;
            var r = recMan.DeleteRecord(model.EntityName, id);
            if (r.Success)
            {
                connection.CommitTransaction();
                transactionStarted = false;
                results.Add(BulkOk(id, "Record deleted."));
            }
            else
            {
                SafeRollbackBulk(connection, ref transactionStarted, "BulkDelete", model.EntityName, id);
                LogBulkFailure("BulkDelete", model.EntityName, id, DescribeBulkFailure(r), null);
                results.Add(MapBulkFailure(id, r, "The record could not be deleted."));
            }
        }
        catch (Exception ex)   // one record fails, the batch keeps going
        {
            SafeRollbackBulk(connection, ref transactionStarted, "BulkDelete", model.EntityName, id);
            LogBulkFailure("BulkDelete", model.EntityName, id, null, ex);
            results.Add(BulkFail(id, "error", "The record could not be deleted."));
        }
    }
}
return BuildBulkResponse(results, "deleted");   // 200 all ok, 207 mixed, 422 none
Architecture

Best-effort partial failure

  • The server processes every selected record.
  • Each record gets its own transaction, so one failure never aborts the batch.
  • The response carries a per-record list with an id, a success flag, a status code, and a message.
  • The endpoint returns 200 when every record succeeds, 207 when some succeed and some fail, and 422 when none succeed, so the client reports which records succeeded and which did not.

Per-record result

{ recordId, success, code, message }

The grid reloads on a full or partial success, a partial success also shows a short summary, and a full failure reports an error without reloading.

Resilience

Authorization stays strict

Default RecordManager

The bulk path uses the default manager, so ignoreSecurity stays false and hooks stay enabled.

Delete permission

Delete checks EntityPermission.Delete once for every record.

Update permission

Archive checks EntityPermission.Update once for every record.

The feature reuses the existing RecordManager permission gate, so each record clears the same entity check a single-record action clears. On top of that gate, the bulk routes add a request-origin guard against cross-site posts and an explicit archive-field update check, and they weaken no existing check.

Security

Archive without new schema

  • Archive sets the existing is_archived boolean to true through a partial update, so no other field changes.
  • PcGrid confirms the entity metadata defines is_archived as a boolean checkbox field before it offers the action.
  • When the entity does not define that field as a checkbox, Archive disables itself for that grid.
  • The feature adds no schema and no migration.

Data Model

Backward compatibility

  • The new options default to off.
  • With bulk actions off, PcGrid renders byte-for-byte as it does today: no toolbar, no checkbox, no script.
  • Every new element is gated on the master option.
  • Disabled grids carry zero runtime cost from the feature.

Opt in per grid

An administrator turns on bulk actions, bulk delete, and bulk archive in the Page Builder, and names the entity for the request.
